# 2026-05-14

## 오늘 한 작업 요약

- Spring 설정을 `application.properties`, `application-dev.properties`, `application-docker.properties`로 분리했다.
- `application.properties`는 공통 설정만 두고, 기본 프로필을 `dev`로 설정했다.
- `application-dev.properties`는 로컬 실행 전용으로 정리했다.
  - DB/Redis host는 `localhost`
  - 민감정보와 환경 의존 값은 `${...}` 로 참조
- `application-docker.properties`는 Docker 실행 전용으로 정리했다.
  - DB host는 `mysql`
  - Redis host는 `redis`
  - `server.origin`은 `${SERVER_ORIGIN}` 으로 외부 접근 주소를 받도록 정리
  - `resource.path`는 `${RESOURCE_PATH}` 로 분리

## 환경변수 / .env 관련 정리

- `src/main/resources/.env`는 Spring이 자동으로 읽는 파일이 아니다.
- 로컬 실행 시 `${...}` 값은 IDE 실행 설정, OS 환경변수, 또는 EnvFile 플러그인 같은 실행 도구가 JVM에 넣어줘야 한다.
- Docker에서는 `env_file`과 Compose 변수 치환이 서로 다른 개념이라는 점을 확인했다.
  - `env_file`: 컨테이너 내부 환경변수 주입
  - `${...}` 치환: Compose 파일 파싱 시점에 필요
- `docker compose`에서 `${DB_PASSWORD}`, `${DB_SCHEMA}` 경고가 난 이유는 `.env.docker`가 `env_file`로만 연결되어 있었기 때문이다.
- 해결 방향은 두 가지로 정리했다.
  - `docker compose --env-file ...`
  - 또는 `docker/auto/.env` 파일명 사용

## Docker 구조 정리

- `docker/dev/docker-compose.yml`
  - 로컬 개발용
  - MySQL, Redis만 실행
  - 앱은 로컬 JVM에서 직접 실행
  - MySQL/Redis 포트 노출 필요
- `docker/auto/docker-compose.yml`
  - 자동 실행용
  - MySQL, Redis, app 함께 실행
  - `SPRING_PROFILES_ACTIVE=docker` 사용
  - app 포트만 외부 노출

## Docker 관련 판단/설명

- `server.origin`은 컨테이너 내부 주소가 아니라 외부 브라우저가 실제로 접근하는 주소다.
- `application-docker.properties`의 Kakao redirect URI도 `${SERVER_ORIGIN}/login/oauth2/code/kakao` 형태로 외부 접근 주소 기준으로 정리했다.
- `dev`에서는 DB/Redis 포트를 호스트에 열어야 한다.
- `auto`에서는 앱이 컨테이너 내부에서 `mysql`, `redis` 서비스명으로 통신하므로 DB/Redis 포트 포워딩이 필수는 아니다.

## Docker 실행 중 발생한 문제와 원인

### 1. MySQL 3306 포트 충돌

- `docker/dev` 실행 시 `3306` 포트가 이미 사용 중이라 MySQL 컨테이너가 시작되지 않았다.
- 원인은 Windows 서비스 `MySQL80`이 `mysqld.exe`로 3306을 점유 중이었기 때문이다.
- 이 문제는 로컬 MySQL 서비스 중지 또는 다른 포트 사용으로 해결 가능하다.

### 2. 컨테이너 이름 충돌

- `ornably-mysql` 컨테이너가 `Created` 상태로 남아 있어서 새 Compose 실행 시 이름 충돌이 났다.
- 실행 중은 아니어도 컨테이너 객체가 남아 있으면 같은 이름을 다시 쓸 수 없다는 점을 확인했다.

### 3. 로컬 실행 실패 원인

- 로컬 IntelliJ 실행에서 `server.port=${SERVER_PORT}` 해석 실패가 발생했다.
- 원인은 `application-dev.properties`는 정상 적용됐지만, `.env` 값이 JVM에 주입되지 않았기 때문이다.
- 즉 설정 구조 문제라기보다 실행 환경변수 주입 문제였다.
- 이후 로컬 실행은 정상 동작하는 상태까지 확인했다.

## MyBatis 경고

- 실행 로그의 `No MyBatis mapper was found in '[bugsandwich.ornably]' package` 는 경고다.
- 현재 프로젝트는 XML mapper와 Repository 중심 구조라서, 인터페이스 기반 `@Mapper` 스캔 결과가 없어서 뜬 것으로 판단했다.
- 앱이 정상 실행되면 지금 당장 치명적인 문제는 아니다.

## Dockerfile 관련 정리

- Docker 자동 실행을 위해 루트 `Dockerfile`이 필요하다고 정리했다.
- 현재 프로젝트는 `war` 패키징이다.
- Spring Boot의 실행 가능한 `war`는 `java -jar app.war` 형태로 직접 실행할 수 있다.
- 즉 외부 Tomcat 컨테이너를 따로 올리지 않아도 된다.
- 포트폴리오/구조 측면에서 멀티스테이지 Dockerfile을 쓰는 방향이 적절하다고 판단했다.

## 개념 정리

- 전통적인 `war`의 목적은 외부 Tomcat 같은 웹 컨테이너에 배포하는 것이다.
- Spring Boot는 `war`도 내장 톰캣 포함 실행 가능하게 확장해 놓았기 때문에 `java -jar`가 가능하다.
- `Tomcat`은 자바 웹앱 실행기이고, `Nginx`는 앞단 프록시/라우터 역할이라는 점을 정리했다.

## 현재 상태 판정

- `application.properties`: 공통 설정 파일로 정리됨
- `application-dev.properties`: 로컬 실행용으로 정리됨
- `application-docker.properties`: Docker 실행용으로 정리됨
- `docker/dev`: 로컬 개발용 구조로 정리됨
- `docker/auto`: 자동 실행용 구조로 정리 중이며, `--env-file` 사용 방식까지 확인됨
- 로컬 실행은 현재 정상 동작 확인
